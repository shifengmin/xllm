> 适用场景：**本机（编辑/分析）+ 构建机（编译/单测）+ 运行机（容器内跑真实负载）** 的三段式远端开发环境。
> 本文不绑定任何模块、模型或方案，出现的数字/文件名只作示例。
> 唯一目的：把「看起来绿了」和「真的验过了」区分开。
>
> 文中 `rrun` 只是本环境「把脚本经 stdin 送到远端」的工具（见全局 `AGENTS.md`）；
> 换到别的环境时，用任何等价的「脚本化投递 + 本地语法预检」方式替代即可。

---

## 0. 三条铁律

1. **远端命令一律脚本化传输**（stdin + base64），绝不在命令行里拼多层引号。
2. **长任务必须脱离会话**（`setsid nohup ... &`）+ 日志文件 + 短探针读取；**退出码不是远端状态的判据**。
3. **每个 PASS 都要配一个「本该 FAIL」的双胞胎**。没有双胞胎的 PASS 只说明你没看见问题。

## 1. 远端执行：脚本化，不内联

```bash
# ✅ 脚本经 stdin + base64，内容不经过任何 shell 解析；发送前本地 bash -n 预检
rrun <target> < inner.sh                       # 远端 bash -s
rrun <target> python3 - < inner.py             # 远端 python
rrun <target> docker exec -i <ctr> bash -s -- a b < inner.sh   # 容器内
rrun -F <ssh-config> <target> < inner.sh       # 自定义 ssh config

# ❌ 禁止：ssh 'docker exec C bash -lc "echo (x)"'
# ❌ 禁止：ssh "python3 -c \"…\""、手工拼 '"'"'、单引号内用 \" 转义
```

判据：远端命令里出现 `(` `)` `` ` `` `$` `!` 或需要换行 → **写成脚本文件再送**，不要内联。
大于 200 字符也一样。长任务不要用「`sleep N; ssh …` 轮询」，每次轮询都是一整轮模型往返。

---

## 2. 长任务：脱离会话（最容易踩、代价最大）

**症状**：本地拿到 `rc=0`，远端任务却在中途被切断——日志停在某一步之后，后续步骤从未发生。
稳定复现的形态：某一步有 1~2 分钟没有 stdout（构建输出被重定向进日志、场景运行本身安静），
会话就在这时断掉。

**机制未定**（可能是远端会话超时/进程组被收），但不必等定论，按下面写就没事：

```bash
# ✅ 完全脱离会话：新会话 + 忽略 HUP + stdin 断开 + 输出进日志
setsid nohup bash "$SCRIPT" > /tmp/job.log 2>&1 < /dev/null &
echo "launched pid $!"
```

```bash
# ✅ 之后用「短探针」读状态，一次探针 = 一条短命令
grep -nE "^########|DONE|VERDICT|error" /tmp/job.log | tail -20
ps -ef | grep -c "[m]y_script"
```

**配套要求**：
* 脚本自己要把**每一个阶段**写进日志（`echo "=== step X ==="`），否则切断点无法定位。
* 阶段之间不要长时间无输出；没有输出就打印心跳。
* 远端 `nohup` 起来的任务**不会**给你任何完成通知，只能靠日志轮询（轮询用短命令，别用长 `sleep` 挂在一个会话里）。

## 3. 文件同步（staging）：无损判据与落地校验

### 3.1 「无损」的判据必须在 stage **之前**
```
✅ 判据： local == remote(在 stage 之前)
❌ 判据： local == remote(在 stage 之后)      # 恒真，掩盖覆盖
```
**真实事故形态**：远端某个文件被远端脚本 patch 过（比如脚本往配置/环境文件里插了一段），
本地副本没有那段。一次「全量 stage」把它覆盖回去，功能静默降级成环境类报错，
而 stage 之后的 md5 对比却显示「一致」。

**规则**：
* 凡是**远端被脚本改过**的文件，本地副本必须先吃进同样的 patch，再纳入 stage 范围；
* 维护一个**只允许脚本改、且必须折回本地**的清单；
* 每次 stage 后核对「本地 md5 == 远端 md5」，同时**核对远端那一份在 stage 前也有同样的 md5**（即 stage 前先抓一次快照做对比）。

### 3.2 派生/辅助文件要一起 stage
不要手挑「本次用到的两个脚本」。凡是验收会用到的工具（比较器、检查脚本、场景驱动、辅助库）
都属于交付物；漏 stage 的症状是「新工具永远留在本机，远端结果仍是旧版」。
**推荐做法**：用通配（`tools/*.py`、`scripts/*.sh`）生成 stage 清单，而不是白名单。

### 3.3 跨平台打包会夹带元数据
macOS 上 `tar`/`zip` 会在 Linux 目标侧留下 `._*`（AppleDouble）垃圾文件；
在目标侧 `rm -f ._*` 清掉，否则会污染目录列表甚至被构建系统扫到。

### 3.4 落地校验（防「把 base64 文本当源码写进去」）
```bash
# 目标侧：体积 + 首行必须像源码；md5 与本地一致
ls -l "$DEST"; head -c 80 "$DEST"; md5sum "$DEST"
```
一次真实事故：生成脚本漏了 `| base64 -d`，把 base64 文本当源码写进了目标树。
症状是**编译器报错里回显一整行巨大的 base64**——看到这种报错，第一反应查同步，而不是查代码。

## 4. 生成脚本自身的自检（写生成器的坑）

生成器（本机生成一段远端脚本文本）是高频事故源，因为它有两层 shell。

| 坑 | 症状 | 改法 |
|---|---|---|
| 忘了 `\| base64 -d` | 目标文件是 base64 文本；编译报错回显巨大 base64 行 | 解码侧固定写 `base64 -d > file <<'EOF'`；解码后立刻打印体积/首字节 |
| 单引号里写 `$VAR` | 生成脚本在远端 `set -u` 下报 `VAR: unbound variable` | 想让**生成脚本**展开就在生成器里展开（用双引号或 `$( )`）；想让它**运行时**展开就写进生成脚本自己的变量表 |
| 哈希/路径清单手工维护两遍 | 两侧列表不一致，校验永远不过或永远过 | 生成脚本自带 `FILES='...'`，期望值与实际值都从同一个列表循环出来 |

**必做**：
1. 生成完立刻 `bash -n <generated>`；
2. 生成脚本里带一段 **decode sanity**（逐文件打印体积 + 首字节），人一眼能看出是文本还是 base64；
3. 需要比对哈希时，生成脚本里也内嵌「期望列表」，让远端自己 diff，而不是靠人眼。

## 5. 构建：增量、日志、失败即停

* **先看构建退出码，再看测试结果**。构建失败时，上一轮的可执行文件仍然躺在输出目录里，
  直接跑测试会得到**「全部通过」的假绿**——这是最隐蔽的一类误判。
  ```
  ninja ... > /tmp/build.log 2>&1; rc=$?; echo "BUILD_RC=$rc"
  [ $rc -eq 0 ] || { grep -nE "error:" /tmp/build.log | head -30; exit 1; }
  ```
* 完整日志留在远端文件里，只回传 `error:` 行与 `tail`，不要把整个日志拉回来。
* 只看**第一条**错误：编译错误的尾部往往是级联噪声，头部才有真因。
* 增量构建要确认「我改的文件真的被重编了」（看日志里的目标/时间戳）；改了头文件要确认依赖它的目标都重编。
* 生成物/第三方子模块也是输入：子模块指针一动、或源码包里缺文件（构建时报某个 patch/脚本不存在），
  症状是构建早期就挂，和被测代码无关。

## 6. 单测与夹具

* **夹具要与「生产者」的公式对齐**（生产代码怎么算形状/偏移，夹具就照那个公式生成），
  并且用**实测形状**校正一次。手编一个「看起来合理」的形状，会让测试和实现一起偏离真实布局。
* **期望值写死并注释「为什么是这个值」**，这样顺序/偏移被交换时测试会 FAIL。
  只断言「大小相等」无法发现「两段互换了」。
* 失败时先判定是**实现错**还是**期望错**——真实事故：实现正确、期望里多算了一个偏移，
  测试报错，差点去改对的代码。看断言的实际值，反推它对应哪种语义。
* **接受用例与拒绝用例成对**：能支持 ×1、不能支持 ×N（每种拒绝理由一个用例）。
  拒绝用例的错误信息要断言到关键词，否则「因为别的原因失败」也算了。
* **不支持的形状必须显式拒绝**，且在**推导阶段**（而不是运行到一半）拒绝；
  禁止「静默近似」「静默跳过然后判 PASS」。
* 夹具辅助函数尽量**复用生产公式**（能调用生产里的纯函数就调用），少写第二份几何算术。

## 7. 验收判据的设计（最容易自欺的部分）

* **鉴别力（负控制）**：同一个比较器，作用在**错的**输入上必须 FAIL。
  做法：① 造一个「本该 FAIL」的孪生用例；② 或者用另一条已知不正确的路径跑同一套比较器。
  没有这一条，比较器「全绿」可能只是它什么都没看。
* **「两边都是空/零」不算 match**。比较器要显式区分 `zero`（无人写）/`absent`（源里没有）/`match`。
  实现方式：先算「全零摘要」，目标摘要等于全零摘要就记 zero，源端索引只收非零摘要。
* **「无法判定」必须是独立结论**，绝不能混进 PASS。缺少必要元数据时输出 `ungraded` 并让整体 FAIL。
* **取「被测动作之前」的状态做判定**。动作之后的快照混入了后续步骤自己的写入，
  会把「正确」误判成 mismatch。
* **源端索引要对同一阶段的所有快照取并集**，只取第一个会漏掉后面才出现的单元。
* **粒度要与改动粒度一致**：改的是「一个整体里的某个子维度」，比较器就必须按那个子维度比；
  按整块比只能证明「没变」或「变了」，不能证明「变对了」。
* **覆盖类计数与放置类计数一起看**：
  `match / misplaced（含发现位置）/ missing / zero` + `source pairs / not delivered / unexpected`。
  只有放置计数会漏「少搬了」，只有覆盖计数会漏「搬错位置」。

## 8. 部署与换件

```bash
# 构建 → 裁剪 → 传 → 校验 → 换入 → 证明新代码在里面
strip <artifact> ; md5sum <artifact>
scp <artifact> <runtime-host>:<path> ;  # 目标侧 md5 必须等于源侧
docker cp <artifact> <ctr>:/tmp/new ; docker exec <ctr> <install-inner.sh>
md5sum <installed-path>                          # 与源侧一致
strings -a <installed-path> | grep -c "<本改动新增的错误串/符号>"   # ≥1 才算真的换上了
```
* **裁剪后再传**（示例：500MB 级的链接产物 `strip` 后 ~110MB，跨机传输时间差一个数量级）。
* **区分两条交付路**：①「打包安装」（真正交付形态，要定期走一次）；②「换单文件」（调试快路，省时间）。
  只走②会有交付形态从未被验证的风险，要在文档里写明。
* **同架构、同镜像**才能换件；换的是运行机上真正被加载的那一份（注意 site-packages 与镜像内副本的区别）。
* **换了二进制就必须复跑上一轮的回归集**：回归矩阵是对**二进制**的验收，不是对源码的。
  只跑新功能的用例，等于放弃了「没回归」这个结论。
* 换件后先用 `strings`/hash 证明新代码在里面，再开始跑场景；否则可能整轮都在测旧二进制。

## 9. 环境类失败 vs 代码类失败

先排除环境，再怀疑代码。二者的分辨信号：

| 信号 | 归类 | 处理 |
|---|---|---|
| `xxx op ... not in libopapi.so` / `not found` | 环境（算子/vendor） | 查算子是否存在于某个 vendor；查查找顺序 |
| 挂载点为空 / 路径不存在 | 环境（挂载） | 宿主侧重挂载后**必须重启容器**（bind mount 不跟随宿主侧重挂） |
| 端口被占 / 设备内存被占 | 环境（残留进程） | 每轮从干净状态开始：先彻底停掉上一轮（只 `pkill` 有时不够，重启容器最稳） |
| 断言失败 / 计数不符 / 字节不一致 | 代码 | 用 §7 的判据定位 |
| 同一场景时好时坏 | 环境或竞态 | 先做「同输入重复 N 次」判稳定性 |

**算子查找顺序**：环境变量给出的自定义算子路径**先于**配置文件里的 vendor 优先级列表被搜索。
所以：
* 临时挂一个算子，用环境变量注入（改环境文件），影响面最小；
* 用安装脚本装 vendor 会**改全局配置文件**（常见行为是**前插**优先级），装完必须核对顺序，
  否则会改变其他算子的解析顺序；
* 排查「算子找不到」最快的一步：`strings <libcust_opapi.so 等> | grep <算子名>`。

## 10. 状态沉淀（为下一个 agent 省时间）

* **单一恢复点**：当前结论 / 未决问题 / 关键产物 hash / 归档标签（含时间戳）/ 环境事实。
  每次同步到构建机与运行机的共享目录，并在恢复点里写下「本文件在两处的 md5」。
* **记录根因，也记录被推翻的早期结论**。错误结论留在文档里比没有结论更贵——
  下一个 agent 会继承一个错前提并据此做决策。推翻时写明「旧结论 + 为什么错 + 新证据」。
* 归档要给**唯一标签**（场景/路线/参数/时间戳），并把「哪一次跑出了什么结论」写进文档。
* 只读探针要幂等，不写状态；诊断脚本不要顺手改环境。

## 11. 提交与格式

* **固定格式化工具版本**。系统装的版本与仓库要求不一致时，装到临时目录用绝对路径调用：
  ```bash
  python3 -m pip install --quiet --target /tmp/fmt "clang-format==20.1.6"
  /tmp/fmt/bin/clang-format --version
  /tmp/fmt/bin/clang-format -i <files>
  ```
* **只 stage 明确的文件**（不要 `git add -A`）：工作区常驻子模块变更、临时产物、未跟踪文档。
* 钩子会 **stash 未暂存文件**再跑检查（日志里会写 `Unstaged files detected`）：
  先 stage 你真正要提交的，再看钩子动了谁；被钩子改过的文件要重新 `add`。
* 代码与文档**分开提交**，提交信息按仓库规范；文档提交里写清「结论 + 证据 + 归档标签」。

## 12. 验收前自检清单

```
[ ] 构建退出码为 0，且日志里能看到我改的文件被重编
[ ] 测试跑的是**本次构建**的二进制（时间戳/hash 确认），不是缓存
[ ] 新加的用例里有「本该 FAIL」的孪生用例，且它确实 FAIL
[ ] 支持用例与拒绝用例成对；拒绝信息断言到关键词
[ ] 判定用的是「被测动作之前」的状态；源端索引取并集
[ ] 比较器能区分 zero / absent / match；无法判定时输出 ungraded 并 FAIL
[ ] 覆盖计数（delivered / unexpected）与放置计数一起看
[ ] 部署件 md5 两侧一致；strings/hash 证明新代码已在运行机上
[ ] 本轮二进制跑了上一轮的回归集，结论写进文档
[ ] 场景/参数/归档标签/产物 hash 写进恢复点，并同步到两台远端
[ ] 长任务都是 setsid nohup + 日志；结论从日志读，不是从退出码读
[ ] stage 前抓过远端快照，确认「本地 == 远端（stage 前）」；被远端 patch 过的文件已折回本地
[ ] 生成脚本过了 bash -n，解码侧有 sanity 打印，两侧哈希用同一个列表循环比对
```

## 13. 反模式速查

| ❌ 反模式 | ✅ 正确做法 |
|---|---|
| `ssh host '...嵌套引号...'` | 写脚本 → `rrun` |
| `sleep N; ssh host 看结果` 轮询 | 远端 `nohup` + 日志；短探针 |
| 长任务挂在 ssh 会话里，用 `rc` 判断成败 | `setsid nohup … < /dev/null &`；从日志判断 |
| 构建失败后直接跑测试，看到「全部通过」 | 先看 `BUILD_RC`；失败即停 |
| 只跑新功能用例就宣布没回归 | 复跑上一轮回归集（针对本次二进制） |
| 比较器只有 PASS 没有鉴别用例 | 加「本该 FAIL」的孪生用例 |
| 目标全零被算成 match | 显式 `zero` 计数；源索引只收非零 |
| 缺少元数据时静默跳过并 PASS | 输出 `ungraded` 并让整体 FAIL |
| 用「动作之后」的快照做判定 | 用「动作之前」的快照 |
| 期望值只写大小、不写顺序 | 写死关键偏移并注释理由 |
| stage 后比对 md5 就认为无损 | 比对 stage **之前**的快照 |
| 手挑两个脚本 stage | 通配全部验收工具 |
| 安装 vendor 后不核对全局优先级 | 装完核对顺序，环境变量注入优先 |
| 宿主侧重挂载后不重启容器 | 重挂后重启容器 |
| 「算子找不到」先去改代码 | 先按 §9 排环境 |

## 14. 一句话总结

**失败很少来自被测代码本身，多来自「同步、构建、判定、会话」这四处。**
把这四处都做成可核对、可复现、带负控制的形式，结论才站得住。
